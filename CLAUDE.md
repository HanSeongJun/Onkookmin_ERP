# Food ERP (사내 ERP)

## Project

- In-house ERP for ONE Korean food-ingredient distribution company (식자재 유통). Single tenant: no organization/tenant columns, no billing, no multi-company logic.
- Every product is a food product. Design every inventory, purchasing and sales feature around the food rules below.
- Users are employees. An admin creates accounts in the Supabase dashboard (Authentication → Users → Add user). There is no public sign-up page — never add one.
- The owner is a non-developer. Always reply in Korean, explain plainly (define any technical term in one short sentence), and give exact copy-paste steps (terminal commands, dashboard menu paths) for anything they must do themselves.
- Naming: the goods this company sells are **상품** (products) everywhere — UI text, menus, code (`products`). Do not use "품목"/"items".

## Stack & versions

- Next.js 16.4 (App Router, `src/` dir, Turbopack), React 19.3, TypeScript 5 (strict).
- `next.config.ts` enables `cacheComponents: true` and `partialPrefetching: true` — keep both.
- Tailwind CSS v4: CSS-first config in `src/app/globals.css` (no `tailwind.config.js`).
- shadcn/ui style `base-nova` = Base UI primitives (`@base-ui/react`), NOT Radix.
- Supabase (Postgres 17 + Auth) via `@supabase/ssr` 0.12 and `@supabase/supabase-js` 2.
- zod 4, react-hook-form 7 + `@hookform/resolvers` 5, `@tanstack/react-table` 9, date-fns 4, lucide-react, sonner.
- Font: Paperlogy (페이퍼로지), self-hosted `.woff2` in `src/app/fonts/` loaded with `next/font/local` (see "UI style"). The `pretendard` npm package is no longer used.

**Next.js 16 differs from your training data.** Read the matching guide in `node_modules/next/dist/docs/` before writing Next-specific code. In particular:

- Middleware is now **Proxy**: `src/proxy.ts` exporting `proxy` (`01-app/01-getting-started/16-proxy.md`).
- With Cache Components, reading `cookies()`/`headers()` outside a `<Suspense>` boundary is a **build error**. Anything that calls `getCurrentUser()`/`requireUser()` must render inside `<Suspense>` (`01-app/02-guides/authentication-with-cache-components.md`).
- `createClient()` from `@/lib/supabase/server` calls `cookies()` and then `connection()` (Supabase compares token expiry with `Date.now()`, which Cache Components only allows at request time). Never call it, or `getCurrentUser()`/`requireUser()`, inside a `"use cache"` or `"use cache: private"` scope. The same applies to query helpers built on it (e.g. `getCategoryTree()`).
- Read a component's source in `src/components/ui/` before using it: Base UI uses a `render` prop instead of `asChild`, and other props differ from Radix-era examples.

### Two databases: hosted (real) and local (for development)

- **Hosted project** = the real company database. `.env.local` points the app at it; never edit `.env.local`. `db:push`/`db:types` need `npx supabase login` and a one-time `npx supabase link --project-ref <id>`.
  - `npm run db:push` changes the real database: show the owner the migration and get an explicit OK before running it. After a push, `npm run db:types` must produce the same `src/types/database.ts` as the local command below.
  - After `src/types/database.ts` changes (db:types or a local regen), **restart the owner's long-running `next dev`** (`lsof -ti tcp:3001 -sTCP:LISTEN | xargs kill`, `rm -rf .next/dev`, start again). On 2026-10-23 a dev server running since the day before kept an old `database.ts` module, so `z.enum(Constants.public.Enums.expiry_kind)` saw `undefined` and the dashboard crashed with "Cannot convert undefined or null to object" although the file and `npm run build` were fine.
  - Hosted settings (auth, sign-up) are changed in the Supabase dashboard; `supabase/config.toml` does not affect the hosted project.
- **Local stack** = a throwaway copy of Supabase running in Docker (OrbStack) on this Mac, for developing and testing migrations. `supabase/config.toml` configures it.
  - Start/stop is done by the owner: `npx supabase start` / `npx supabase stop` (first start downloads images and can take ~15 minutes). Check it with `npx supabase status` (`-o env` prints the local URLs and keys).
  - Local URLs: API `http://127.0.0.1:54321`, Studio (local dashboard) `http://127.0.0.1:54323`, Mailpit (test e-mails) `http://127.0.0.1:54324`, Postgres port 54322.
  - Apply all migrations + test data from scratch: `npx supabase db reset` (local only; NEVER add `--linked`). It runs `supabase/migrations/*` then `supabase/seed.sql`.
  - Regenerate types from the local DB (use this while a migration is not pushed yet). The local generator prints unformatted code and leaves out the `__InternalSupabase` block that the hosted one adds (it tells supabase-js the PostgREST version, 14.18 both locally and hosted, which enables types such as `.maxAffected()`). So:
    1. `npx supabase gen types typescript --local --schema public > supabase/.temp/database.ts.tmp`
    2. `npx prettier --ignore-path /dev/null --parser typescript --write supabase/.temp/database.ts.tmp`
    3. Copy the `__InternalSupabase` block (with its two comment lines) from the current `src/types/database.ts` into the new file as the first property of `Database`, then `mv supabase/.temp/database.ts.tmp src/types/database.ts`.
       The result matches `npm run db:types` except for `ComputedFields: never` lines and the order of view relationships, which is fine.
  - SQL console: `docker exec -i $(docker ps --format '{{.Names}}' | grep '^supabase_db_') psql -U postgres -d postgres`
  - Run the app against the local stack (process env overrides `.env.local`; the keys are local-only test keys — never write them into a project file):
    `NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321 NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=<PUBLISHABLE_KEY from npx supabase status -o env> npx next dev -p 3101`
    Afterwards stop it (`lsof -ti tcp:3101 -sTCP:LISTEN | xargs kill` — without `-sTCP:LISTEN`, lsof also lists the owner's Chrome processes that merely have a connection to that port, and they would be killed too) and run `rm -rf .next/dev` so the local values are not left in the dev cache. Only one `next dev` may run in this project at a time. When the owner's `next dev` is running, use `next build` then `next start -p <port>` with the same two env vars instead (a build keeps `.next/dev`, so the dev server keeps working; only one build at a time). Afterwards run a plain `npm run build` so `.next` no longer holds the local values.
  - Local test users: create them in local Studio (Authentication → Add user, tick Auto Confirm). Gotcha: in `config.toml`, sign-up is blocked by `[auth] enable_signup = false`; `[auth.email] enable_signup` must be `true`, otherwise the CLI turns off e-mail/password login entirely on the local stack ("Email logins are disabled").

## Conventions

- UI text: natural Korean. Code identifiers and comments: English.
- Keep code simple, explicit and conventional; no clever abstractions. The owner must be able to follow it.
- Server Components by default; add `"use client"` only for interactivity. Mutations go through Server Actions validated with zod.
- Supabase: `@/lib/supabase/server` in server code, `@/lib/supabase/client` in Client Components; both typed with `Database`.
- Auth: check in server code (pages, Server Actions, Route Handlers) with `@/lib/auth/user` — the proxy is only a first gate. Never trust `getSession()` alone on the server.
- Env vars: only `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (see `.env.example`). Never add a service-role/secret key to this app, and never expose one to the browser. Data protection comes from RLS.
- Money: integer KRW stored as `bigint` (원 단위). Never float, never decimal money.
- Prices are typed and stored **VAT-inclusive (부가세 포함)**; the 부가세 별도 amount and the 부가세 are always computed, never stored. Rules and helpers: "가격과 부가세" below.
- Quantities: `numeric` with an explicit unit column next to it. Never an implicit unit.
- Timestamps: `timestamptz`; display in `Asia/Seoul`. Calendar dates (e.g. 소비기한) use `date`.
- Tables: English snake_case plural names; `id`, `created_at timestamptz default now()`, `updated_at` on every table.
- Every new table gets `enable row level security` + its policies **in the same migration**, plus explicit `grant`s to `authenticated` (and `revoke` from `anon`): new tables are not exposed to the API automatically.
- **Saving rows of several tables at once** (e.g. a 묶음상품 and its 구성표) goes through ONE database function called with `supabase.rpc(...)`, never through several API requests (a failed second request would leave half a save). Pattern (see `create_bundle_product` / `update_bundle_product`): `language plpgsql`, `security invoker` (runs with the employee's own RLS and privileges), `set search_path = ''` (full `public.` names), JSON arguments in DB column names, optimistic concurrency by comparing `updated_at` inside the function after `select … for update`, and `revoke all … from public, anon, authenticated` + `grant execute … to authenticated, service_role` (Supabase grants new functions to anon by default).
  - **Exception: the 재고 save functions are `security definer`** (receive_stock, issue_stock, dispose_stock, transfer_stock, apply_stock_count, reverse_stock_document, import_opening_stock). The stock tables must be writable ONLY through them (append-only ledger, balances = Σ lines), so employees have no INSERT/UPDATE/DELETE privilege on those tables at all; the functions run as the owner, check every value, record `auth.uid()`, and only `authenticated`/`service_role` may EXECUTE them. Read functions stay `security invoker`.
- **Errors raised by our own functions/triggers**: `raise exception '<Korean message for the user>' using errcode = …, hint = '<english_key>'`. The Server Action switches on `error.hint` (keys in `PRODUCT_DB_RULES`, `@/lib/products/constants`; `PARTNER_DB_RULES`, `@/lib/partners/constants`) to put `error.message` under the right field; plain constraint violations are still matched by constraint name (`PRODUCT_DB_CONSTRAINTS`, `PARTNER_DB_CONSTRAINTS`).
  - Never use `errcode = 'no_data_found'` (P0002): the API (PostgREST 14) answers it with a plain-text "500 Something went wrong", so the message and hint are lost. Leave the errcode out (default P0001) or use a 22xxx/23xxx code; those come back as JSON with the hint.
  - In a CHECK, write `x is not null and x >= 0`, not just `x >= 0`: a comparison with null is "unknown", and a CHECK lets "unknown" pass.
- Rules that must hold even when two employees save at the same moment (e.g. "no 사용 묶음상품 with a 사용중지 기준상품") are enforced by triggers that lock the rows they read with `FOR SHARE` (READ COMMITTED), not only by app checks.
- Optional text columns store `null`, never `''`; text is stored trimmed (the DB checks this).
- Schema changes only via `supabase/migrations` (`npm run db:new`), never by hand in the dashboard. Test with `npx supabase db reset` locally, regenerate types, and push only with the owner's OK.
- **A migration that was pushed to the hosted DB is never edited** (the hosted DB never runs a file again, so the change would silently be missing there). ## 상품관리 (products) — decisions made by the owner

- Tables: `product_categories` (상품 분류), `products` (상품: 기준상품 and 묶음상품) and `product_bundle_items` (묶음상품 구성표); migrations listed under Conventions. Every signed-in employee may read/add/change them (구성표 rows may also be deleted); anon gets nothing.
- **No deleting products.** Use 사용 여부 (`is_active`; default 사용). Products have no DELETE privilege at all. The list has no 삭제 button: checked rows are switched with **선택 사용중지 / 선택 사용** (confirm dialog with the count, Korean toast with the result).
- **상품코드** (`code`): typed by the user (they have their own code scheme), editable later. Trimmed, 1–30 of letters, digits, `.`, `_`, `-`. Unique ignoring case ("a001" = "A001"). ### 기준상품 / 묶음상품 — decided by the owner (2026-10-21)

- **Our ERP always counts single units ("개입").** Every product is one of two types (`products.product_type`, enum `product_type`):
  - **기준상품** (`base`, UI "기준상품" / "기준상품(개입)", list badge "기준"): one single unit, e.g. "스팸 클래식 1.81kg" (1 캔). It is the **top-level code** and holds all food information.
  - **묶음상품** (`bundle`, UI "묶음상품", badge "묶음"): a 구성표 of one or more 기준상품 × 수량, e.g. "[묶음] 스팸 클래식 1.81kg X 6개입" (스팸 × 6), "[박스] … X 24개입" (스팸 × 24) or a mixed set (스팸 × 2 + 참치 × 3). Not called 모자코드/세트코드 in the UI.
- The type is chosen on 등록 and **never changes** (trigger `products_keep_product_type`, hint `product_type_fixed`).
- **구성표** = table `product_bundle_items` (`bundle_id`, `component_id`, `quantity` integer 1–100000 in the 기준상품's own unit, `sort_order`; primary key `(bundle_id, component_id)` instead of an `id` column; both foreign keys `on delete restrict`). Rules (trigger `check_product_bundle_item`, locks both rows `FOR SHARE`): components are **기준상품 only** (no bundle inside a bundle), the parent must be a 묶음상품, a 기준상품 appears **at most once** per 묶음상품, **at least one row**. The last rule is checked by the database when the transaction commits (deferred constraint triggers `products_bundle_has_items` on a new 묶음상품 and `product_bundle_items_keep_one` on deleting/moving a 구성표 row, function `check_bundle_has_items`, hint `bundle_items_empty`), so direct API writes cannot leave an empty 묶음상품 either; the save functions also refuse an empty 구성표 up front. Consequences: a 묶음상품 and its 구성표 rows must be added in ONE transaction (the RPCs do; `seed.sql` relies on `db reset` running it as one transaction), and a 묶음상품 can only be deleted (admins/tests only; the app never deletes) together with its 구성표 rows in one `begin … commit`.
- A 묶음상품 has its own 상품코드 (same uniqueness rules), 상품명, 규격, 단위, 매입가/판매가 (부가세 포함 integer KRW), 바코드, 사용 여부, 비고 and its own optional 분류 (미분류 allowed). It has **no food information of its own**: the DB check `products_product_type_fields_check` keeps `storage_type`, `tax_type`, `origin`, `manufacturer`, `shelf_life_days` null and `allergens = '{}'` for 묶음상품 (and requires 보관온도/과세구분 for 기준상품).
- **Derived food information** of a 묶음상품 (never typed), in the view `product_list_items` as `effective_*` columns (for a 기준상품 they equal its own values) and in JS as `deriveBundleFoodInfo` (`@/lib/products/bundle`, used by the modal and `getProduct().foodInfo`) — **change both together**:
  - 보관온도 = the strictest (냉동 > 냉장 > 상온; enum order, `max()`);
  - 과세구분 = 과세 if all are 과세, 면세 if all are 면세, otherwise **혼합** (`effective_tax_type = 'mixed'`, `EffectiveTaxType`, label "혼합");
  - 알레르기 = union (the app sorts it in the law's order);
  - 유통기한 기준일수 = the minimum of the filled-in ones;
  - 원산지 / 제조사 = the distinct values, sorted by character code (`collate "C"` in SQL, default `sort()` in JS), joined with ", ".
  - The view also has `component_count` (0 for 기준상품) and, for a 묶음상품 of one kind of 기준상품, `single_component_id/_code/_quantity`. The list's 구성 column uses `formatComposition` ("×6", "혼합 2종").
- **혼합 과세**: a 혼합 묶음상품's own prices are stored as one VAT-inclusive amount each; its 부가세 is worked out by splitting that amount by its 기준상품's prices (rule in "가격과 부가세"). The UI shows 과세구분 "혼합".
- **Saving**: 기준상품 are inserted/updated directly (`products`). 묶음상품 are saved with the RPCs `create_bundle_product(product jsonb, items jsonb) returns uuid` and `update_bundle_product(product_id uuid, loaded_updated_at timestamptz, product jsonb, items jsonb) returns uuid` (product + whole 구성표 in one transaction; ≥1 item, ≤100, no duplicates; `product_changed` when `updated_at` differs). `update_bundle_product` switches a bundle OFF before replacing the 구성표 and ON only after it, so the activation check sees the new 구성표.
- **사용 여부 rules**:
  - Switching a 기준상품 to 사용중지 **automatically switches off every 사용 묶음상품 that contains it** (AFTER trigger `products_deactivate_bundles`; works for single saves and 선택 사용중지 alike). The UI warns first with the count: the 상품 수정 modal reads the 묶음상품 again with `loadBundlesContainingProduct` when 저장 is pressed and shows the count + their names ("이 기준상품이 들어간 묶음상품 N개도 함께 사용중지됩니다"); 선택 사용중지 uses `countBundlesToDeactivate` ("체크한 기준상품이 들어간 묶음상품 N개도 …"). Results report `bundlesDeactivated`.
  - Switching the 기준상품 on again does **not** switch its 묶음상품 on.
  - A 묶음상품 cannot be switched on (or saved as 사용, or get a 사용중지 기준상품 while 사용) while any of its 기준상품 is 사용중지 (trigger `products_check_bundle_activation`, hint `bundle_activation_blocked`; `check_product_bundle_item`, hint `bundle_component_inactive`). 선택 사용 switches 기준상품 first, then 묶음상품, and skips (reports `blocked`) the ones still blocked.
  - Both triggers lock the rows they read (`FOR SHARE`), so two employees saving at the same moment can never leave a 사용 묶음상품 with a 사용중지 기준상품 (tested with racing sessions).
- **Data layer**: `productFormSchema` is a zod discriminated union on `productType` (`baseProductFormSchema` | `bundleProductFormSchema`), typed with the flat `ProductFormInput` (one form object holding the fields of both types; the other type's fields are dropped). 구성표 rows are `items: { componentId, quantity }[]`; 구성표-wide errors are reported under the field name `items`. `getProduct()` returns `components` (묶음상품), `bundles` (기준상품: the 묶음상품 containing it; with `salePriceInclVat`/`salePriceExclVat`) and `foodInfo`. Price fields: see "가격과 부가세". ### 가격과 부가세 — decided by the owner (2026-10-22)

- **Users type prices only VAT-inclusive (부가세 포함).** The DB stores exactly what was typed: `products.purchase_price_incl_vat` (기본 매입가) and `products.sale_price_incl_vat` (기본 판매가), integer won, ≥ 0, optional. The 부가세 별도 amount (and the 부가세) is shown next to it, read-only, everywhere a price appears (list grid, 상품단가 tab, 묶음상품 price references, 엑셀). Price sort/filter, if added, uses the VAT-inclusive value.
- **Never store the 부가세 별도 amount, and never recompute 포함 from 별도** (12,000 → 별도 10,910 → ×1.1 = 12,001: the typed price would change). Always compute 별도 from the stored 포함 amount.
- **부가세 below 1 원 is cut off (버림).** For a VAT-inclusive amount P:
  - 과세: 부가세 = floor(P ÷ 11), 부가세 별도 = P − 부가세 (12,000 → 1,090 / 10,910; 1,358 → 123 / 1,235);
  - 면세: 부가세 = 0, 부가세 별도 = P.
  - (A negative amount, e.g. a refund in 정산, gives the same numbers with a minus sign.)
- **혼합 묶음상품 (과세 + 면세 기준상품): split P by the 기준상품's price ratio** — the future **정산 module must use this same rule** (call the SQL helpers or `@/lib/products/vat`, don't re-implement it):
  - weights: 과세 weight = Σ (과세 기준상품 price × 수량), total weight = Σ (every 기준상품 price × 수량), VAT-inclusive prices; the 판매가 is split by the 기준상품's 판매가, the 매입가 by their 매입가;
  - 과세 part T = round(P × 과세 weight ÷ total weight), 0.5 rounded up (computed with whole numbers only: floor((2·P·과세 weight + total weight) ÷ (2·total weight)));
  - 면세 part = P − T, 부가세 = floor(T ÷ 11), 부가세 별도 = P − 부가세;
  - when any 기준상품 has no such price (null), or the total weight is 0, the split is impossible: 부가세 별도/부가세 are null and the UI shows "-" (the 포함 price is still shown).
- **Changing a product's 과세구분 keeps its stored VAT-inclusive price**; the 별도 amount follows automatically.
- Where the rules live — **change both together**:
  - SQL (migration 4): `vat_excluded_amount(amount_incl bigint, taxable boolean)`, `mixed_taxable_amount(amount_incl, taxable_weight numeric, total_weight numeric)` (T), `mixed_vat_excluded_amount(…)` — immutable, `search_path = ''`, execute for `authenticated` and `service_role` only. The view `product_list_items` uses them for `purchase_price_excl_vat`, `purchase_vat`, `sale_price_excl_vat`, `sale_vat` (null when not computable).
  - TS: `@/lib/products/vat` (client-safe): `vatOf`, `excludedOf`, `mixedWeights`, `allocateMixed`, `splitVat`; `@/lib/products/bundle`: `componentVatWeights`, `splitBundlePrice` (a 묶음상품's price by its effective 과세구분), `perUnitPrice`, `componentPriceTotal`. Used for the modal's live preview and wherever the view's columns are not available. A parity test (TS vs SQL over every amount 0..200,000, sampled 혼합 splits, edge cases and the view) matched exactly when this was written; rerun one after changing either side.
- Code names: form fields `purchasePriceInclVat` / `salePriceInclVat` (zod labels "기본 매입가(부가세 포함)" / "기본 판매가(부가세 포함)"); list rows `purchasePriceInclVat`, `purchasePriceExclVat`, `purchaseVat`, `salePriceInclVat`, `salePriceExclVat`, `saleVat` (`ProductListRow`); `BaseProductOption.purchasePriceInclVat` / `salePriceInclVat`.
- RPC JSON keys of `create_bundle_product` / `update_bundle_product` are `purchase_price_incl_vat` / `sale_price_incl_vat`. The old keys `purchase_price` / `sale_price` are refused (hint `price_keys_renamed`), so an old app cannot silently save empty prices.
- Migration 4 did NOT change any existing amount: before it the price columns were labelled 부가세 별도, but the owner confirmed (2026-10-22) that the prices already in the real DB had been typed 부가세 포함, so only the columns were renamed.

## 자료일괄등록 (bulk registration from Excel) — decided 2026-10-22

- **What**: register 상품분류, 상품 (기준상품 + 묶음상품), 거래처, 직원 and 기초재고 from an Excel (.xlsx) or CSV file. - **Flow** (same on every screen; code in `src/lib/imports/`, one spec per kind: `PRODUCT_CATEGORY_IMPORT`, `PRODUCT_IMPORT`, `PARTNER_IMPORT`, `EMPLOYEE_IMPORT`, map `kind` → spec as the UI needs):
  1. [양식 다운로드] `downloadImportTemplate(spec)` (`@/lib/imports/download`, browser): data sheet(s) with a brand-colored title row (required titles end with "*", frozen), 500 empty rows pre-formatted as text for code/phone columns (Excel keeps 00123 and 3-15), then 작성방법 (every column: 필수, 형식, 입력할 수 있는 값, 예시, 설명) and 예시 sheet(s). Examples live ONLY in the 예시 sheets, which are never read, so they cannot be imported by accident.

Titles are matched by name in any order, ignoring spaces, "*", brackets (also full-width) and case (`matchKey`; `aliases` too, e.g. our 엑셀 download titles); a missing required title is an error, unknown titles only a warning (a title in a column's `notAccepted`, e.g. ‘매입가’/‘판매가’ which other programs often mean without 부가세, is not read and gets its own note asking to rename it); blank rows skipped; at most 3,000 data rows (`IMPORT_MAX_ROWS`) in all sheets; ≤ 20MB file; a cell longer than `IMPORT_CELL_MAX_CHARS` (10,000) is cut to that length (its column rule then reports it). Date cells become "YYYY-MM-DD".
     - .xlsx extras from `scanXlsx` (`@/lib/imports/xlsx-scan`: reads the zip's XML with the browser's DecompressionStream; returns null on anything unexpected, then the file is read as before): **hidden sheets are never read** (a file whose only matching sheet is hidden gets a message saying so); **another visible sheet with every required title and data is never skipped silently**: a note ("‘Sheet2’ 시트는 읽지 않았습니다") when every data sheet was found by its template name, an error ("한 시트에 모으거나 파일을 나눠서") when a sheet was only guessed by its titles (e.g. 거래처 split into 매출처/매입처 sheets); **merged cells** within one column below the title row are read as the top cell's value in every row (note "세로로 병합된 칸 … 같은 값"; rows whose only values come from a merge are blank); **formula errors** (#N/A, #REF! …, read as empty by read-excel-file) become `ImportRawRow.flags[column] = "#N/A"` → a cell error "엑셀 수식 오류(#N/A)…" (rows with no value of their own, e.g. a VLOOKUP copied below the data, stay blank); a **date cell in a column that is not `dateColumn`** gets flag "date" → a yellow note (Excel turns 3-15 into a date); **number cells with an all-zero format** ("000000") are read as the text Excel shows (124 → "000124"). Every check calls `addCellFlags(issues, raw)` (`@/lib/imports/check`) first.
  3. 미리보기: Server Action `validate<Kind>Import(input)` with `input = { sheets: importSheetsInput(result.sheets), createMissingCategories }` → `ImportValidateResult` (`{ ok, preview }`): every row `ImportRowResult` (`sheet`, `excelRow`, `status` "ok" | "error" | "skipped" = 정상/오류/건너뜀 (`IMPORT_ROW_STATUS_LABELS`), `errors`/`warnings` as `{ column (column key) | null, message }`, `note` such as "자동 0015", "새 분류 2개", "구성 2종", "이미 있음"), totals `total/ok/error/skipped`, `newCategories` (paths the import will create). [오류 목록 엑셀로 받기] = `downloadImportErrors(spec, sheets, preview)`: the 오류 rows with the same titles plus "원래 행" and "오류 내용" (cells with errors in red), named like the template's sheets so the fixed file can be uploaded again.
  4. [정상 M건 등록]: `commit<Kind>Import(input, okRowKeys)` (`okRowKeys` = `importRowKey(row)` of the 정상 rows) → `ImportCommitResult`. ## 재고관리 (inventory) — decided by the owner (2026-10-23)

- **Stock = lots × locations, only for 기준상품.** A lot (`stock_lots`) is one 기준상품 received once: `lot_no` (typed, unique per 상품 ignoring case, or automatic `L<전표일자>-<NNN>`), `supplier_lot_no` (공급처 로트, free text, for recalls), `expiry_kind` (`use_by` 소비기한 / `sell_by` 유통기한 / `none`; date required iff not none), `expiry_date`, `manufactured_date` (≤ 입고일 ≤ …, ≤ 기한일), `received_date`, `unit_cost_incl_vat` (부가세 포함, optional), `supplier_id` (매입처/매출·매입 거래처), `origin`, `memo`, `created_document_id`. Lots never change after saving. A location is 창고 (`warehouses`) > 구역 (`warehouse_zones`, with `storage_type` 상온/냉장/냉동) > 위치/선반 (`storage_locations`, e.g. "B-02-R02"). Codes: letters/digits/Hangul/`._-`, 창고 ≤ 20 unique ignoring case, 구역 ≤ 20 unique per 창고, 위치 ≤ 30 unique per 구역 (`STOCK_PLACE_CODE_PATTERN`, DB `is_stock_place_code`). Every 구역 gets a "기본" 위치 (`is_default`, trigger) that can never be deleted or lose the mark; a 구역 never moves to another 창고, a 위치 never to another 구역. Delete (창고 → its 구역 → 위치, cascade) works only while nothing was ever stored there (FK restrict from balances/movements); otherwise 사용중지. New stock goes only into a 위치 whose 위치, 구역 and 창고 are all 사용; stock can always leave.
- **Ledger** (`stock_documents` + `stock_movements`): every change is a 전표 of `doc_type` opening 기초재고 / receipt 입고 / issue 출고 / disposal 폐기 / transfer 이동 / count 실사조정 / reversal 취소, `doc_no` "<기초|입고|출고|폐기|이동|실사|취소>-YYYYMMDD-NNN" (per kind and 전표 date, `stock_number_counters`), `doc_date` (Korea date; back-dating allowed; later dates up to today + `app_settings.future_doc_days` = 예정 전표, see "전표 일자와 예정 전표"), `partner_id`, `memo`, `request_id` (the same save sent twice is saved once). Lines: lot, location, signed `quantity_delta` (numeric(14,3), ≠ 0), `line_no` (the screen line; 묶음상품 and FEFO splits share it), `seq` (saving order), `reason` (폐기 only), `memo`, `bundle_id`/`bundle_quantity` (line came from a 묶음상품), and filled by the trigger: `product_id`, `unit_cost_incl_vat` (lot's), `doc_date`, `movement_type` (for 취소 lines: the kind they undo), `is_reversal`, `reverses_movement_id`. **Append-only**: no UPDATE/DELETE/TRUNCATE (triggers, even for the owner; hint `stock_ledger_append_only`); a 전표 header only ever gets its 취소 mark (`reversed_by_id`, `reversed_at`). A 전표 needs ≥ 1 line (commit-time constraint trigger).
- **Balances** (`stock_balances`, one row per (lot, location), `quantity ≥ 0` CHECK) change ONLY through the trigger on new lines (a direct insert/update/delete is refused: trigger depth check), so they always equal Σ lines. `stock_integrity_check()` (run in the SQL console: `select * from public.stock_integrity_check();`, empty = fine) proves it plus: no negative balance now or at any earlier moment, lines match their lot and 전표, lots only of 기준상품, every lot has its receiving line, every 취소 is the exact opposite of its 전표.
- **No negative stock, ever**: the CHECK on balances, and the history rule for every 전표 date: lines are ordered by (`doc_date`, `seq`) — a new line comes after every line of its own date — and the running balance of each (lot, location) must never go below 0 on any day (`stock_pair_at` / `stock_available_from`: what a new line dated D may take = the smallest running balance from D on; `check_stock_document_history` re-checks, after saving, every pair the 전표 took from that has lines dated after it; `check_stock_pair_history`, hint `stock_history_negative`). These per-date numbers (and `stock_integrity_check`, the ledger's 잔량) use the view `stock_history_lines` (migration 9): every line except, for a 전표 undone ON ITS OWN DATE, its lines that took stock and their 취소 lines — that 전표 never took stock on any day (a cancelled 새벽배송 출고 frees its stock at once, also for today). Leaving out such a pair (− then + on one day) only raises the balances between them, so it never breaks the rule; end-of-day stock is the same. A lot never moves before its 입고일 (`stock_date_before_receipt`).
- **Who writes**: employees read everything; 창고·구역·위치 and `app_settings` are edited directly (column grants: 창고 code/name/address/note/is_active/sort_order, 구역 code/name/storage_type/note/is_active/sort_order, 위치 code/name/is_active/sort_order, settings expiry_warning_days, future_doc_days); stock tables only through the `security definer` save functions (see Conventions). anon: nothing.
- **Concurrency**: functions that take stock lock the lots first (`lock_stock_lots`: one statement, ordered by id, FOR NO KEY UPDATE), then read quantities again; numbers come from counter rows (≤ 1 document and ≤ 1 lot counter per transaction, in that order); the same `request_id` waits on an advisory lock. Tested: 3 sessions issuing one lot (2 saved, 1 "재고 부족", never negative), transfer vs issue both orders, count vs issue (count refused: `stock_count_changed`), 60 documents with opposite product order in parallel (no deadlock), 10 parallel receipts (unique numbers), same 로트번호 / same 취소 / same request at once.
- **FEFO** (`stock_issue_plan`, used by `plan_stock_issue` (preview), `allocate_fefo(product, quantity, …, plan_date)` (one product; the future 주문 module calls it with the 출고 date) and `issue_stock`): lots with a 기한 before lots without; earliest 기한일; earliest 입고일; older lot (created_at, id); within a lot 창고·구역·위치 code. Everything is seen from the 전표 date D: never a lot whose 기한일 < D (기한 경과; a 기한 ending ON D may go; `include_expired` only for previews), never a lot received after D, and from each (lot, 위치) at most what a new line dated D may take (`stock_pair_at.available`: stock that later 전표 use or that arrives after D is left out, so FEFO takes other lots); optional filter per line (창고/구역/위치). The candidates of each 기준상품 (with the date-aware numbers, one window pass over the pairs that have lines after D) are read once per plan and shared by its lines (3,000-line plan ≈ 1.4 s with 예정 lines). Several lines of one product share its stock: lines limited to a 위치 are planned first, then 구역, then 창고, then the lines without a limit, each group in line order (a simple rule, not a full search; the result is in line order again), so "line 1: 10 anywhere, line 2: 3 at 위치 A" fits whenever the total does. Each demand reports `taken_by_other_lines` (stock at its places that lines planned before it took; TS `IssueDemand.takenByOtherLines`), `reserved_later` (stock there at the end of D that 전표 dated after D use; `reservedLater`) and `arriving_later` (stock that comes only after D; `arrivingLater`). Not enough → `stock_insufficient` with the product, needed and available quantity on that date ("오늘" / "10-24에") and what is left out (`stock_shortage_notes`: other lines' share, 기한 경과, "내일 이후 전표가 쓰는 재고", "내일 이후 들어오는 재고" — "10-25 이후" for other dates; TS `shortageText(demand, planDate)` uses the same words); nothing saved.
- **묶음상품** in 입고/출고 are split by their 구성표 (`stock_bundle_components`): quantity × 구성 수량 per 기준상품 (each its own lot on 입고, same 기한 unless worked out per 기준상품 from 제조일자); the 입고 단가 (per 묶음상품) is shared per unit: `price_weight` = round(단가 × 기본 매입가 ÷ Σ(기본 매입가 × 구성 수량)) (same arithmetic as `mixed_taxable_amount`), or `quantity` = round(단가 ÷ Σ 구성 수량) when a 기준상품 has no 기본 매입가; whole won per 기준상품 unit, so the lots' worth differs from the typed amount by up to 0.5원 × Σ 구성 수량 per 묶음상품 — growing with the quantity received (1,000 박스 × 24 @ 551,990원 → lots worth 552,000,000원, +10,000원). Therefore the 입고 line keeps the typed 단가 per 묶음상품 (`stock_movements.bundle_unit_cost_incl_vat`, copied to its 취소) and the 전표's value (`stock_document_list_items.value_in/out_incl_vat`, the 보기 modal's 금액 합계, the 입고 modal's line 금액) is 묶음상품 수량 × that 단가, once per line, exactly as typed; 재고금액 (reports, lots) uses the lots' shares. TS mirror `splitBundleUnitCost` (`@/lib/inventory/constants`; parity tested) — change both together. 기초재고/실사 추가 accept 기준상품 only.
- **Rules of values**: quantities > 0 (실사 counted ≥ 0), ≤ 100,000,000, ≤ 3 decimals, whole numbers except units kg/g/L/mL (`unit_allows_fraction`, TS `unitAllowsFraction`; for a 묶음상품 the converted 기준상품 quantity is checked too).
- **단위 is fixed once a product has stock records** (a 기준상품's lots, a 묶음상품's 입고/출고 lines): every stock quantity is counted in `products.unit` and no unit is stored next to it, so a change would silently relabel the history (12.5 kg → 12.5 박스). Trigger `products_keep_unit_with_stock` (`check_product_unit_change`, hint `product_unit_has_stock` = `PRODUCT_DB_RULES.unitHasStock` → field error on 단위 in `@/lib/products/actions`); `stock_receive_line` locks the product (and a 묶음상품's 기준상품) `FOR SHARE` while it makes their lots, so a 단위 change at the same moment waits and is then refused (race tested). The 상품 수정 modal disables 단위 with a note when `ProductDetail.hasStockRecords` (`getProduct`; false when the 재고 tables are missing). 입고 단가 whole won 0–100억. 기한일 empty + 제조일자 + the product's 유통기한 기준일수 N → 제조일자 + (N − 1) days (제조일 = 1일째; `stock_expiry_from_manufactured`, TS `suggestExpiryDate`). 입고 partner = 매입처/매출·매입 and 사용; 출고 partner any 사용 거래처 (매입처 for 반품). Products must be 사용 for new stock (출고/폐기 of a 사용중지 product's stock still work).
- **기한 상태** (view `lot_stock_items.expiry_status`, TS `expiryStatus`): `expired` 기한 경과 (기한일 < today, Korea), `imminent` 기한 임박 (0 ≤ days left ≤ `app_settings.expiry_warning_days`, default 7, 0–365, 재고 설정), `ok`, `none`. 보관온도: `storage_mismatch` (구역 ≠ 상품), `storage_too_warm` (구역 warmer than needed — dangerous); 입고/이동 save anyway and return `warnings`; `stock_transfer_warnings(lines)` lists them before saving.
- **취소** (`reverse_stock_document(target_document_id, header)`): a 취소 전표 (date ≥ the original's, ≤ today + the setting or the original's date when later — a 예정 전표 can always be undone on its own date; default today, or the original's date of a 예정 전표 — TS `reversalDateRange`; memo default "<전표번호> 취소") with the opposite of every line, both marked; the lines that put stock back are saved first (`order by quantity_delta > 0, seq`), so a chained 이동 (A→B 5, B→C 3, B later partly issued) never goes below 0 for a moment and can be undone whenever the net per (lot, 위치) is there; refused when the stock it takes back cannot go on the 취소 date without leaving a later line short — also a 예정 출고 (`stock_reversal_insufficient`: undo the later 출고/이동 first) — or a back-dated 취소 would break the history while today works (`stock_history_negative`: use today), or a later date within the limit works (`stock_history_negative`, "취소 일자를 <date>(으)로 해 주세요", detail `suggested_date`: e.g. the 출고 that used a 예정 입고 was undone on a later day than its own); a 전표 undone on its own date never took stock (see "No negative stock"), so after a 예정 출고 is undone (default: its own date) the 입고 it used can be undone on its own date too; a 취소 전표 or an undone 전표 cannot be undone again. Reports count a 취소 in the column of the kind it undoes (입고 취소 lowers 입고).
- **실사** (`stock_count_sheet(warehouse, zone, location, as_of)` → lines with 전산 수량 at the end of that date (as_of up to today + the setting: 예정 전표 up to then counted), ≤ 3,000; `apply_stock_count(header, lines, new_lots)`): only differences become ± lines; each line sends the `system_quantity` it showed — if the stock changed since, nothing is saved (`stock_count_changed`); found stock without a lot → `new_lots` (new lot, 입고일 = 실사 date); a decrease must leave the lines dated after the count enough (`stock_history_negative`: "오늘 날짜로 실사해 주세요" for a back-dated count, "뒤 날짜의 전표(예정 출고 등)를 먼저 확인해 주세요" otherwise); a counted line that puts stock where its lot had none that day needs a 사용 위치 (`check_stock_input_location`, like 입고); no difference at all → `stock_count_no_difference`. ## Food-domain rules (for upcoming modules)

- **Lots/batches**: stock is tracked per lot (lot number, 입고일, 제조일자, 유통기한/소비기한, quantity, storage location). On-hand stock = sum of lot quantities; never a single editable number on the product. Every change is a stock movement row (입고/출고/조정/폐기) with who and when.
- **유통기한 vs 소비기한**: Korea labels most foods with 소비기한 (use-by) since 2023; some products still carry 유통기한 (sell-by). Store the date as `date` plus which kind it is, and show the matching Korean label. `products.shelf_life_days` is only a default for computing a lot's date from its 제조일자.
- **보관온도**: every product has a storage type — 상온 (room temp), 냉장 (refrigerated, 0–10 °C), 냉동 (frozen, −18 °C or below). Locations have a storage type too; warn when they don't match.
- **FEFO**: outbound allocation picks the lot with the earliest expiry first (First Expired, First Out), tie-break by 입고일. Never allocate lots expired on the 출고 date (a 출고 dated tomorrow judges 기한 by tomorrow), never stock that arrives after it or that later-dated 전표 need; surface "expiring soon" lots on the dashboard.
- **원산지**: country/region of origin per product, and per lot when it varies by supplier.
- **알레르기 유발물질**: allergens per 식품 등의 표시·광고에 관한 법률 시행규칙 [별표 2] (19 items as of 2026-10; a 2026-08 draft would add 참깨·들깨·아몬드·캐슈너트), stored as a list of keys per product.
- **Units**: for now each product has exactly ONE unit (kg, 박스, 개 ...), and quantities are in that unit. No unit conversion yet (e.g. 1 박스 = 10 kg); it may be added later as a separate table, without changing `products.unit`. A 묶음상품's 구성표 quantity is in its 기준상품's unit.
- **Stock lives only on 기준상품.** Inventory, purchasing and sales (lots, stock movements, FEFO, orders) keep quantities ONLY for 기준상품. A 묶음상품 in an order/receipt/shipment is converted through its 구성표 into 기준상품 quantities (e.g. 2 × "[박스] 스팸 X 24개입" = 48 스팸) before touching stock; never store stock for a 묶음상품.
